rec = corrupt(make_record(rng, i), tier, rng, prev_invoice_no)

You are not labelling documents. You are manufacturing documents from labels. The answer exists before the artefact does, so it can never drift from it. Reverse this and you are hand-labelling PDFs at midnight — which nobody finishes, which means no eval, which means you are back to guessing.
Step 6

Look at how the damage is made

Open 02-generator/chaos.py and find _swap_digits:

for a, b in zip(digits, digits[1:]):
    if s[a] != s[b]:   # skip EQUAL pairs, deliberately
        ls[a], ls[b] = ls[b], ls[a]
        return float("".join(ls))
Why that one line is there It swaps the first unequal pair of digits. If it swapped two identical digits, it would record "I broke this document" while changing nothing — and later your scorer would report a miss that never existed. A chaos engine has to guarantee its chaos is real. Everything it does is logged to corruptions, which is what lets you slice your score by exactly what was done.

Step 9b

If you picked Track B or C — use the dedicated sheet

Your track has its own step sheet Track B (paid API) → open docs/Workshop-Steps-TrackB.html
Track C (framework) → open docs/Workshop-Steps-TrackC.html

Each one has its own numbered steps, its own checks, and its own failure list — including the ones that do not look like failures. The summary below is the short version; the sheets are what you actually follow.
Both of these are untested Track A was run end to end many times and every number we quote for it is measured. Tracks B and C have never been executed — we had no API keys during the pre-flight. They were corrected from the provider docs, not from a green test. Run --limit 1 first, and read the error on the first row rather than the wall of them.

Track B — the paid API. You are here for one line of code:

tool_choice={"type": "tool", "name": "record_invoice"}

Forced tool choice makes the model answer through your schema instead of writing prose you dig JSON out of. No markdown fences, no coerce_json(), no regex. That is what "structured output" actually means, and the pattern outlives the vendor.

Be precise about what it buys you A forced tool call guarantees you get a tool_use block. It does not guarantee that block validates against your schema — the parameter for that is strict: true, which needs additionalProperties: false, which pydantic does not emit. So the shape is guaranteed by construction and correctness is still caught by Invoice.model_validate(). Structured output removes a class of parsing bugs. It does not remove your validation layer.

Track C — the framework. Two stages: LlamaParse turns any document — scans, rotated tables, a 40-page contract — into clean markdown, then stage 2 extracts against the same Invoice schema.

And be honest about the trade For today's invoices this is arguably overkill — our PDFs are born-digital, so pdfplumber already reads a perfect text layer for free (that is G4, and Track A proves it at 8 s/doc for ₹0). Stage 1 earns its keep on documents you cannot read for free. The cost is three unpinned packages and a model lookup that happens inside the framework before any request is sent. The framework buys you stage 1; the schema and validators stay yours.
What Track B costs — estimated, not measured At Sonnet 5's published $2 / $10 per million tokens, one of our one-page invoices is roughly 2,500 input + 350 output tokens ≈ $0.0085 ≈ ₹0.75/doc. So ≈ ₹75 for today's hundred — and ≈ ₹7.5 lakh at a million documents a month. That second number is a headcount.

It is an estimate: the code never reads resp.usage, so the repo cannot tell you what a document actually cost. That is gotcha G6 happening in our own code, on the one track that could measure it.
If you see Every document says ERR and your score is 0% — a request parameter was rejected. This does not crash: the retry fires, the runner catches per document, and you get a full 100-row file with zero fields. Read the error text on row 1.
B: authentication_error — ANTHROPIC_API_KEY=sk-ant-… in the repo-root .env.
B: an unexplained ValidationError on a long invoice — that is max_tokens truncation, not a schema problem. Raise TRACK_B_MAX_TOKENS.
C: ModuleNotFoundError: llama_cloud_services — the llama-index lines in requirements.txt are commented out on purpose. Uncomment and pip install — at home, it is a heavy install.
C: it raises inside Anthropic(...) before any network call — llama-index keeps its own model registry. Upgrade llama-index-llms-anthropic, or pass --model with an id it knows.
C: missing LLAMA_CLOUD_API_KEY — stage 1 needs it. Stage 2 runs on your local model by default, so there is no second key.

Step 12

Read the report in this order — not top to bottom

  1. Slice before you believe the headline. One number for a whole pipeline hides everything. Look at every tier column. The hardest tier is often worst — but not always, and where your difficulty actually lives is the finding.
  2. Recall, then precision. "10/10 caught" looks perfect until you see it also flagged 52 of your 60 clean documents. A validator that flags everything scores 100% recall and is useless. Both numbers or neither.
  3. Headline versus parsed-only. If parsed-only is much higher, your problem is stability, not accuracy — and that is a different fix.
  4. Exact versus normalized. The gap between them is your post-processing spec, written for you for free.
  5. Cost at your real volume. ₹50 per 100 documents feels free. The same number at a million documents a month is a headcount.
Why there are two scores for every field 
Ground truth: 1,82,336.22      Parser said: 182336.22
exact  ✗       normalized  ✓
(Indian digit grouping, from the reference build — the same gap shows up in whatever your document formats oddly.) Those are the same answer. A scorer that only does exact matching marks it wrong and sends you off debugging a parser that works perfectly. Normalize both sides — normalizing only the parser's output silently grades your truth file's formatting choices instead.

Step 13

Change one thing, and score it into a new file

# never overwrite your first score
python track_a_local.py --text-fallback --dataset ../02-generator/dataset

python eval.py --outputs ../03-parser/outputs_track_a.jsonl \
               --truth ../02-generator/dataset/ground_truth.jsonl \

  1. Diagnose from the report first. Which field, which tier, and how is it wrong? Print a few rows next to the truth and look.
  2. Change exactly one thing — a prompt rule, a validator, a normalization gap.
  3. Compare per field, not headline.
What happened when we did this We added three prompt rules and the score fell: 71.8% → 66.6%. Obvious call — revert it.

But two fields we hadn't touched dropped from 100% to 86%, exactly matching 14 new failed documents. Scoring both runs on only the documents that survived both: 70.9% versus 72.1%. The new prompt was better the whole time — one bad rule was hiding two good ones. Removing just that rule gave 72.9%, and one field went from 24% to 57%.

If we had read only the headline, we would have thrown away a real improvement.
Before you finish A second score, at least one tier column that moved, and one sentence about why it moved.
