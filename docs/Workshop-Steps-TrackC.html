Track C — the framework

LlamaParse turns any document into markdown; then you extract against the same schema — on your own machine, so this track needs one key and costs ₹0. You are here to find out what a framework buys you, and what it charges.

This track has now been run end to end All 100 documents, both stages, zero errors — 82.8% at 23.5 s/doc on an 8 GB M2. Every number on this page is measured, not quoted from documentation.

Still start at --limit 1: your install and your key are not ours.
Why

The two-stage pattern

This is the shape most real document pipelines end up in, and it is worth seeing even if you would not choose it today.

The idea

Parse first, extract second

PDF ──► LlamaParse ──► markdown
                          │
                          ▼
              extract against Invoice

Stage 1 turns any document into clean markdown — a scan, a rotated table, a 40-page contract. Stage 2 is plain text extraction against the same schema.Invoice every other track uses. The framework buys you stage 1. It is genuinely the part you would not want to build.

We expected this to be overkill here. It is not — and the numbers say why Same 100 documents, same schema, same validators, same scorer, and the same local model in stage 2 — so the only variable is LlamaParse vs pdfplumber:

Track A 72.9%  →  Track C 82.8%, and C wins every line-item field: rate +24, amount +15, HSN +15, description +12, qty +7. It loses only on total (−8).

This is not about text fidelity — pdfplumber reads the characters perfectly. It is about structure. LlamaParse hands the model a markdown table with named columns; pdfplumber hands it a flat run of numbers the model has to segment itself. Give a small model a table and it stops guessing which number is the rate and which is the amount.

The price is real: 3× the latency (23.5 s vs 8.2 s), a LlamaParse page per document, a ~180 MB install, and three unpinned packages. Whether +9.9 points is worth that is now a decision you can make with numbers instead of taste.
Before

Install — at home, not at the venue

Step C1

Uncomment the dependencies and install them

The llama-index lines in requirements.txt are commented out on purpose — the install is heavy and it is not fair to make forty people download it over venue wifi.

# requirements.txt — remove the leading '#' from these three
llama-cloud-services
llama-index-core
llama-index-llms-ollama          # stage 2, local, no key

pip install -r requirements.txt

Only add llama-index-llms-anthropic if you deliberately want the paid stage 2.

Check it worked 
python -c "import llama_cloud_services, llama_index.core; print('ok')"
Step C2

One key — stage 2 runs on your own machine

echo 'LLAMA_CLOUD_API_KEY=llx-...' >> .env   # stage 1 only

Free LlamaParse tier at cloud.llamaindex.ai covers today's hundred pages. Stage 2 defaults to the same local Ollama model Track A already pulled, so this track costs ₹0 and needs no LLM key at all.

Why local is the right default here Track C exists to answer one question: what does the framework's document-conversion stage buy me? Keep stage 2 identical to Track A — same model, same schema, same eval — and the only variable left is LlamaParse vs pdfplumber. That is a clean experiment.

Bolt a paid API onto stage 2 and you have quietly mixed in Track B's question: when your score moves you cannot say whether stage 1 or stage 2 did it. Want the paid path anyway? pip install llama-index-llms-anthropic then python track_c_llamaindex.py --llm anthropic --limit 5.

Step C3

One document, and expect to debug the install before the API

ollama serve &                       # stage 2 runs locally
cd 03-parser
python track_c_llamaindex.py --dataset ../02-generator/dataset --limit 1
Three things fail before the network does — in this order 1 · ModuleNotFoundError: llama_cloud_services — Step C1 not done. This is failure number one for everybody.
2 · It raises inside Anthropic(...) before any request is sent. llama-index ships its own model → context-window registry and looks the id up on construction. A release older than the model you name raises right there. Fix: upgrade llama-index-llms-anthropic, or name one it knows: python track_c_llamaindex.py --model <an id your version knows> --limit 1
3 · Credentials. LLAMA_CLOUD_API_KEY in the repo-root .env. It fails in stage 1, before extraction is ever attempted. On the default local stage 2 that is the only key you need — make sure ollama serve is running instead.
Check it worked A line naming the pipeline — [C] stage 1 LlamaParse -> stage 2 ollama:llama3.2:3b — then [C-llamaindex] inv_0001 OK …s and done: 1 ok, 0 errors. Stage 1 is a network round-trip per document, so expect this to be slower than Track A.
The default that would have cost you the afternoon We hit this for real. llama-index's Ollama defaults context_window=-1 — meaning the model's full window, 131,072 tokens for llama3.2:3b. Ollama dutifully allocates a 128K KV cache on a laptop that cannot afford one, and a 365-token prompt took over three minutes and timed out.

Pinning it to 8192 — the same value Track A measured — took the identical call to 5.5 seconds. It is now pinned in the code (TRACK_C_NUM_CTX to override).

This is the framework tax, exactly: Track A sets num_ctx because we measured it. The abstraction chose a different default and did not mention it.

The comparison that matters Put your row next to Track A's text-path row. Same model, same schema, same scorer — so the only difference is LlamaParse instead of pdfplumber. If the framework pipeline does not beat it on born-digital PDFs, that is not a failure, it is the finding. Report it. The interesting question is what would have to be true about your documents for stage 1 to earn its keep.
One more thing the abstraction takes away Track A hands Ollama the JSON schema through format= — constrained decoding, where the generated tokens literally cannot leave your schema. Going through structured_predict you get the framework's own structured-output handling instead, which on a small local model is closer to prompt-and-parse than a decoding guarantee. Same model, same schema, weaker guarantee. If Track C scores below Track A on identical hardware, look here before you blame LlamaParse.
One more thing you will see on import llama-cloud-services prints a deprecation warning: its stated maintenance window ended 2026-05-01, and the successor is pip install llama-cloud>=1.0. It still works — we kept the package we could actually verify — but do not be surprised. A pinned-and-dying dependency is part of what a framework costs you.
